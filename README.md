# tenderwatch

Детермінований монітор польських публічних тендерів (укриття / *schrony*, *MDS*, подвійного призначення, модульні, оборонна інфраструктура) з **повною історією змін** і **вимірюванням повноти**. Працює на власному VPS, дані в SQLite, дашборд українською, сповіщення в Telegram.

LLM тут не потрібен для щоденної роботи: збір, класифікація, дедуплікація й сповіщення — звичайний код, який можна тестувати й відтворювати. LLM (Claude) доречний поверх БД для сірої зони `review` і для аналітики.

## Чим це відрізняється від попередніх версій

| Проблема | Як закрито |
|---|---|
| Пошук лише по заголовку; «schron» лише в тілі оголошення не знаходився | **sweep**: щоночі забираємо *всі* оголошення за вікно дат і аналізуємо тіло для будівельних CPV (`45*`, `71*`) |
| Сервер мовчки ігнорує невідомі параметри (так було з `TenderId`) | кожна відповідь проходить `check_filter`: якщо фільтр не спрацював — запуск падає, дані не приймаються, приходить сповіщення |
| Джерело «тихо» повертає 0 або змінило схему | `health`: порівняння з медіаною, «застарілі» запуски, помилки розбору; алерт у Telegram з cooldown |
| Немає історії | кожен знімок джерела зберігається (за хешем), зміни дедлайну/назви/вартості/статусу — окремі **події** |
| Дублі між джерелами (pz ↔ e-Zamówienia ↔ TED) | точні ключі (`ocds-id`, номер BZP, TED, id платформи) + обережне нечітке зіставлення (див. нижче) |
| Невідомо, скільки ми пропускаємо | **capture–recapture** між каналами пошуку + «канарки» (`tenderwatch recall`) |
| Повторні публікації (Namysłów — двічі анульовано) | подія `republished`, лічильник спроб на одному записі |

## Архітектура

```
sources/ (ezam, ted, pz, bk)  ──▶  classify (прозорі правила rules.toml)
        │ search: слова + CPV, щогодини                │
        │ sweep : усі оголошення за датами, щоночі     ▼
        └── enrich: тіло оголошення             store.ingest ──▶ tenders / notices / snapshots / events / hits
                                                        │
                       health · recall · reminders ◀────┤
                                                        ▼
                                      Telegram · FastAPI-дашборд · CSV
```

* **e-Zamówienia** — один ендпоїнт `Board/Search` дає і пошук по назві (`OrderObject`), і точний CPV (`CpvCode`), і діапазон дат; деталі — `GetNoticeHtmlBodyById?noticeId=<objectId>`. Усе це **перевірено на живих відповідях 20.09.2026**.
* **TED** — офіційний Search API v3 (POST), запит `buyer-country=POL AND (classification-cpv=…)`. Перевірено на живому API.
* **platformazakupowa.pl** — HTML-лістинг (`.auction-row`), перевірено на живій сторінці. Запити лише послідовні й повільні (паралельні дають 429).
* **bazakonkurencyjnosci.gov.pl** — розбір терплячий, але **схема не підтверджена** (на момент розробки ендпоїнт віддавав 500). Дивіться `tenderwatch doctor`.

### Дедуплікація: чому вона свідомо обережна

Хибне злиття двох різних тендерів гірше за пропущений дубль. Тому нечітке зіставлення (коли точних ключів немає) вимагає: однакових чисел у назвах (`nr 5` ≠ `nr 7`), збігу замовника, для іншого джерела — схожості ≥ 0.93, для того ж джерела — ідентичної назви **і** завершеної попередньої спроби (два одночасні відкриті тендери з однаковою назвою — різні процедури). Якщо кандидатів кілька — розв'язуємо за датою дедлайну, інакше не зливаємо. Найкращий шлях — точний ключ: `pz.enrich` шукає на сторінці процедури номер BZP / `ocds-id`.

## Швидкий старт (локально, для розробки)

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest                                   # 61 тест, мережа не потрібна

export DB_PATH=data/tenderwatch.sqlite3
tenderwatch doctor                                        # жива перевірка джерел
tenderwatch run --mode search --days 90 --quiet           # швидко: слова + CPV за 90 днів
tenderwatch run --mode sweep  --days 14 --quiet           # повільніше: усі оголошення по днях + аналіз тіл
tenderwatch serve                                         # http://127.0.0.1:8000
```

## Розгортання без сервера (рекомендовано): GitHub Actions

Жодного VPS не потрібно. `.github/workflows/{search,sweep,digest,export,doctor}.yml` запускають той самий код за розкладом на тимчасових машинах GitHub, а стан (SQLite-база) зберігається між запусками як asset релізу `state` у самому репозиторії. Сповіщення — лише в Telegram (без постійного веб-дашборду: GitHub Pages не дає безкоштовної авторизації, а віддавати список тендерів у відкритий доступ ми не хочемо).

1. Залийте репозиторій на GitHub (**обов'язково приватний** — усередині ваша бізнес-логіка відбору й дані).
2. Settings → Secrets and variables → Actions → **New repository secret**: додайте `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID`.
3. Settings → Actions → General → Workflow permissions → **Read and write permissions** (потрібно, щоб workflow міг зберігати стан у reliz).
4. Перше наповнення без спаму в Telegram: вкладка **Actions** → workflow **search** → **Run workflow** → `days=90`, `quiet=true` → Run. Тоді workflow **sweep** → `days=14`, `quiet=true` → Run. `sweep` на 14 днів може йти довго (десятки хвилин) — це нормально, просто зачекайте.
5. Далі нічого робити не треба: **search** ходить щогодини, **sweep** — щоночі, **digest** — раз на день (по понеділках із звітом про повноту).
6. Список тендерів CSV-файлом у Telegram — вкладка Actions → workflow **export** → Run workflow, у будь-який момент.
7. Діагностика джерел — Actions → workflow **doctor** → Run workflow, результат дивіться в логах кроку.

Це вкладається у безкоштовний ліміт GitHub Actions (~2000 хв/міс для приватного репозиторію) за звичайного навантаження; якщо перевищите — GitHub рахує копійки (~$0.008/хв), сервер при цьому не потрібен.

## Альтернатива: розгортання на VPS (Docker)

Якщо колись захочете постійний сервер із живим веб-дашбордом — Docker-набір лишився в репозиторії. Достатньо 1 vCPU / 1 ГБ. Потрібні Docker + Compose:

```bash
git clone <ваш репозиторій> tenderwatch && cd tenderwatch
cp .env.example .env && nano .env                         # пароль дашборду, Telegram
docker compose build
docker compose run --rm worker tenderwatch doctor          # усе має бути [OK]
docker compose run --rm worker tenderwatch run --mode search --days 90 --quiet
docker compose run --rm worker tenderwatch run --mode sweep --days 14 --quiet
docker compose up -d                                       # worker + web (127.0.0.1:8000)
docker compose --profile https up -d                       # (опційно) Caddy з HTTPS, потрібен DOMAIN у .env
```

**GitHub Actions CI** (`.github/workflows/ci.yml`): на кожен push — ruff + pytest (Python 3.11/3.12); з `main` — автодеплой по SSH на VPS, якщо задано секрети `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_PATH` (стосується лише цього варіанту, не serverless-шляху вище).

**Бекап (VPS):** `docker compose exec worker tenderwatch backup /data/backup-$(date +%F).sqlite3` — додайте в cron на хості. Для serverless-варіанту копія бази й так лежить у GitHub Releases репозиторію.

## Налаштування пошуку

Уся логіка відбору — у `rules.toml` у корені репозиторію (ключові слова, CPV, вагові коефіцієнти, шумові шаблони, «канарки»). У serverless-варіанті достатньо запушити зміну у `main` — наступний запуск `search`/`sweep` підхопить її сам, окремого перезапуску не треба. Кожне сповіщення в Telegram про новий тендер має розкриті причини («+4 «schron» (назва)», «−4 schronisko»…), тож правила легко підправляти за реальними хибними/пропущеними випадками.

Заповніть `[canaries] ids` реальними `tenderId` (наприклад, Namysłów `ocds-148610-c79171aa-…`): якщо система їх не знає — це видно в `tenderwatch recall`, дашборді («Повнота») та в понеділковому дайджесті.

## Команди

| Команда | Що робить |
|---|---|
| `tenderwatch doctor` | жива діагностика всіх джерел (доступність, схема, чи працюють фільтри) |
| `tenderwatch run [--mode search\|sweep] [--days N] [--sources ezam,ted]` | одноразовий запуск |
| `tenderwatch run --quiet …` | наповнення без сповіщень (для першого запуску) |
| `tenderwatch recall` | оцінка повноти + канарки |
| `tenderwatch status` | стан джерел і лічильники |
| `tenderwatch digest [--send]` | дайджест |
| `tenderwatch export` | CSV у stdout |
| `tenderwatch daemon` / `serve` | воркер / дашборд (лише VPS-варіант) |

## Розклад

**Serverless (GitHub Actions):** розклад заданий у самих `.yml`-файлах у `.github/workflows/` — `search` щогодини (`cron: "0 * * * *"`), `sweep` щоночі, `digest` раз на день. Часи в GitHub Actions — UTC; поточні cron-рядки підібрані під приблизно 02:00 за Варшавою і 07:00 за Києвом, але через літній/зимовий час можуть «пливти» на годину — некритично для щоденного дайджесту.

**VPS (`tenderwatch daemon`):** та сама логіка, але посекундно звірена з поточним часом у процесі: щогодини — `search` (вікно `LOOKBACK_DAYS`), щоночі (02:xx за Варшавою) — `sweep`, о 07:xx за Києвом — дайджест (у понеділок + звіт про повноту), нагадування про дедлайн — за 3 та 1 день. Стан розкладу лежить у БД, тож перезапуски безпечні.

## Що НЕ покрито (чесно)

* Підпорогові (< ~130 тис. PLN) закупівлі, які гміна публікує лише на власному BIP: їх бачимо тільки якщо вони є на platformazakupowa.pl. Перед краулінгом 2825 BIP варто виміряти реальні втрати через `recall`.
* TED шукається лише по CPV (текстовий запит TED не верифіковано). Польські тендери вище порогу однак дублюються в e-Zamówienia.
* Розбір вартості й кількості частин із тіла оголошення — best-effort (поле не обов'язкове для нижчепорогових).
* Невідомі типи оголошень (зміни, виправлення) не відкидаються, а потрапляють у попередження запуску: після першого `backfill` перегляньте `runs.detail` і за потреби уточніть відповідність у `sources/ezam.py::_lifecycle`.
* Оцінка Чепмена припускає незалежність каналів; вони корельовані, тому це нижня межа непомічених.
* Serverless-шлях (GitHub Actions) я не запускав наживо з мого середовища — перевірити зможе лише перший реальний запуск `search`/`sweep`/`doctor` у вашому репозиторії. Найімовірніші проблеми: права `gh release upload` (Workflow permissions), і те, чи впишетесь у безкоштовний ліміт хвилин при активному трафіку тендерів.
* `tenderwatch doctor` повертає ненульовий код виходу, якщо хоч одне джерело `[BAD]` — тому workflow **doctor** може показувати червоний хрестик навіть коли проблема лише в некритичному `bk`. Це очікувано, дивіться деталі в логах кроку.

## Розробка

```bash
ruff check src tests && pytest
```

Нове джерело = клас у `sources/` з `search()` (+ за можливості `sweep()`, `enrich()`, `doctor()`), що повертає `Notice`; решта (класифікація, дедуп, події, сповіщення, здоров'я, повнота) працює без змін. Додавання Литви/Латвії/Естонії/Румунії — це нові джерела на тій самій схемі.
